# CYCLE 03 SPECIFICATION: Web UI Construction (Visualization)

## Summary
The final cycle focuses on the "Presentation Layer", bringing the entire PoC together into an interactive web application using Streamlit. This cycle will implement the user interface that allows users to input a GitHub repository and view the aggregated metrics generated by the previous cycles. The application will serve as a comprehensive dashboard, displaying high-level KPIs (Stars, Forks, Open Issues) alongside detailed visual charts (Commit History trends and Top Committers). A critical requirement for this cycle is robust and user-friendly error handling. The UI must never crash or expose stack traces to the user; instead, any underlying exceptions (like invalid tokens or missing repositories) must be caught by the application controller and translated into clear, helpful alerts on the screen. By the end of this cycle, the project will be a fully functional, deployable dashboard demonstrating the complete E2E flow.

## Infrastructure & Dependencies

### A. Project Secrets (`.env.example`)
*   (No new external service secrets are required. The existing GitHub token remains the only secret.)

### B. System Configurations (`docker-compose.yml`)
*   **Streamlit Configuration**: If deploying via Docker, ensure the default Streamlit port `8501` is exposed.
    *   **Instruction for Coder**: No explicit configuration file changes are strictly necessary for the Python code, but ensure `streamlit run src/presentation/app.py` is the documented entry point.

### C. Sandbox Resilience (CRITICAL TEST STRATEGY)
*   **Mandate Mocking**: Testing the UI layer automatically in a sandbox is challenging. We rely heavily on integration tests of the *Controller* logic that feeds the UI, heavily mocking the API client. UAT via Marimo will serve as the primary validation for the visual components.

## System Architecture
This cycle completes the architecture by adding the Presentation Layer and the central Controller that orchestrates the data flow.

```text
.
├── src/
│   ├── config.py
│   ├── domain/
│   ├── ingestion/
│   ├── processing/
│   └── presentation/
│       ├── __init__.py
│       ├── controller.py     # Orchestrates Ingestion -> Processing
│       └── app.py            # Streamlit UI logic
└── tests/
    └── integration/
        └── test_controller.py
```

*   `src/presentation/controller.py`: The crucial link. It takes a user input (repo name), checks the cache, calls the API if necessary, runs the data through the transformer, and returns a structured object containing the KPIs and DataFrames ready for rendering. This prevents the UI from containing business logic.
*   `src/presentation/app.py`: Contains purely Streamlit (`st.*`) commands. It defines the layout, input fields, error message display logic, and chart rendering.

## Design Architecture
The design architecture in this final layer focuses on the Data Transfer Objects (DTOs) passed from the Controller to the UI.

*   **`DashboardData` DTO**: A new Pydantic model (or a simple Python dataclass) should be defined to encapsulate all data required by the UI for a single rendering pass.
    *   *Fields*: `repo_metadata` (the Pydantic model from Cycle 01), `daily_commits_df` (Polars DataFrame), `top_committers_df` (Polars DataFrame).
    *   *Rationale*: By packaging all necessary data into a single object, the UI code remains clean and only needs to unpack this object to render the various sections.
*   **Exception Translation**: The Controller acts as an anti-corruption layer for errors. It catches `domain.exceptions.*` and translates them into simple, safe string messages that the Streamlit app can display using `st.error()` or `st.warning()`.

## Implementation Approach
1.  **Dependency Addition**: Add `streamlit` to the project dependencies.
2.  **Controller Implementation**: Create `controller.py`. Implement a function `get_dashboard_data(repo_name: str)` that orchestrates the flow: check cache -> if miss, fetch API -> transform data -> update cache -> return combined `DashboardData` object. Implement robust `try...except` blocks here to catch domain exceptions.
3.  **UI Layout**: Create `app.py`. Setup the Streamlit page configuration. Add a text input field for the user to enter the repository name (e.g., "owner/repo").
4.  **Data Binding & Rendering**: Implement the logic so that upon form submission, `get_dashboard_data()` is called.
    *   If successful: Display KPIs using `st.columns` and `st.metric`. Display the DataFrames using `st.line_chart` (for date trends) and `st.bar_chart` (for committers).
    *   If an error string is returned: Display it using `st.error()`.
5.  **Refinement**: Ensure the UI looks clean, with appropriate titles and descriptions.

## Test Strategy

### Unit/Integration Testing Approach
*   **Controller Tests**: Focus heavily on testing `controller.py`. Mock the `github_client` and `cache_manager`.
    *   Test the "Happy Path": Assert that when the API mock returns valid data, the controller correctly pipes it through the transformer and returns a fully populated `DashboardData` object.
    *   Test Error Translation: Configure the API mock to raise an `AuthenticationError`. Assert that the controller catches this and returns a safe error message string instead of crashing.
*   **UI Testing Limitations**: We will not write complex automated tests for the Streamlit UI logic (`app.py`) itself within the standard Pytest suite due to brittleness. Visual correctness is verified via UAT.

### Live E2E Testing
*   A manual (or script-assisted) E2E run using `streamlit run app.py` must be performed. This involves entering a real repository name and visually confirming that the entire pipeline functions correctly from API fetch to chart rendering.
