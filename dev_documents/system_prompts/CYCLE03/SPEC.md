# CYCLE 03 SPECIFICATION: Web UI Construction (Visualization)

## Summary
The third and final development cycle focuses completely on the reactive "Presentation Layer", bringing the entire architectural PoC together into an interactive, user-facing web application leveraging the Streamlit framework. This ultimate cycle will flawlessly implement the visual user interface that allows users to seamlessly input a specific GitHub repository name and instantly view the mathematically aggregated metrics generated by the intricate processing engines developed in the previous cycles. The web application will serve as a comprehensive, high-level dashboard, prominently displaying crucial top-level KPIs (Total Stars, Total Forks, Open Issues) alongside highly detailed, interactive visual charts (chronological Commit History trends and ranked Top Committers). An absolutely critical architectural requirement for this final cycle is the implementation of highly robust, completely user-friendly error handling. The Streamlit UI must mathematically never crash entirely or ever expose raw Python stack traces or HTTP error codes to the end-user; instead, any underlying system exceptions (like invalid authentication tokens or missing remote repositories) must be securely caught by the application controller and smoothly translated into clear, helpful, safe alerts rendered directly on the screen. By the successful end of this cycle, the software project will be a fully functional, easily deployable, robust dashboard demonstrating the complete, unbroken End-to-End data flow.

## System Architecture
This final cycle completes the overarching architecture by seamlessly adding the Presentation Layer and the highly central Controller module that robustly orchestrates the complex data flow between all lower layers.

```text
.
├── src/
│   ├── config.py
│   ├── domain/
│   ├── ingestion/
│   ├── processing/
│   └── presentation/
│       ├── __init__.py
│       ├── controller.py     # Orchestrates Ingestion -> Processing seamlessly
│       └── app.py            # Streamlit reactive UI layout and rendering logic
└── tests/
    └── integration/
        └── test_controller.py
```

*   `src/presentation/controller.py`: The absolutely crucial linking mechanism. It safely takes a raw user input string (the repo name), mathematically checks the local cache manager, calls the external API client only if absolutely necessary, pipes the resulting data cleanly through the Polars transformer, and finally returns a strictly structured Python object explicitly containing all the KPIs and DataFrames completely ready for immediate UI rendering. This fundamentally prevents the UI module from containing any complex business logic.
*   `src/presentation/app.py`: Contains purely declarative Streamlit (`st.*`) rendering commands. It simply defines the visual layout, the input form fields, the safe error message display logic, and the final chart rendering function calls.

## Design Architecture
The specific design architecture in this final presentation layer focuses exclusively on the structured Data Transfer Objects (DTOs) passed cleanly from the Controller directly to the UI rendering engine.

*   **`DashboardData` DTO**: A completely new, strictly typed Pydantic model (or a mathematically simple Python dataclass) must be definitively defined to explicitly encapsulate all the data required by the Streamlit UI for a single, complete rendering pass.
    *   *Fields*: Must include `repo_metadata` (the exact Pydantic model from Cycle 01), `daily_commits_df` (the aggregated Polars DataFrame), and `top_committers_df` (the ranked Polars DataFrame).
    *   *Rationale*: By securely packaging all absolutely necessary mathematical data into a single, cohesive, strictly typed object, the UI rendering code remains incredibly clean and only needs to unpack this single object to instantly render the various dashboard sections.
*   **Exception Translation Anti-Corruption Layer**: The Controller acts mathematically as a highly secure anti-corruption layer for all system errors. It aggressively catches all `domain.exceptions.*` and flawlessly translates them into simple, completely safe string messages that the Streamlit app can display safely using `st.error()` or `st.warning()`.

## Implementation Approach
1.  **Dependency Addition**: Add the `streamlit` UI library to the primary project dependencies using the `uv` package manager.
2.  **Controller Implementation**: Architect and create the `controller.py` module. Implement a highly robust function `get_dashboard_data(repo_name: str)` that completely orchestrates the flow: check cache -> if miss, securely fetch API -> cleanly transform data -> safely update cache -> return the combined, typed `DashboardData` object. Implement highly robust `try...except` blocks here to securely catch all possible domain exceptions.
3.  **UI Layout Definition**: Create the `app.py` module. Setup the primary Streamlit page configuration (title, layout width). Add a highly visible text input field for the user to securely enter the target repository name (strictly in the "owner/repo" string format).
4.  **Data Binding & Visual Rendering**: Implement the core logic so that immediately upon form submission, `get_dashboard_data()` is safely called.
    *   If mathematically successful: Display the KPIs cleanly using `st.columns` and `st.metric`. Display the processed DataFrames interactively using `st.line_chart` (for date-based trends) and `st.bar_chart` (for top committers).
    *   If a safe error string is returned from the controller: Display it highly visibly to the user using the red `st.error()` banner.
5.  **Refinement**: Ensure the final UI looks exceptionally clean, with highly appropriate titles, descriptions, and axis labels for the charts.

## Test Strategy

### Unit/Integration Testing Approach
*   **Controller Tests**: Focus the vast majority of testing effort heavily on testing `controller.py`. Aggressively mock the `github_client` and the `cache_manager`.
    *   Test the "Happy Path": Mathematically assert that when the API mock returns perfectly valid JSON data, the controller correctly pipes it through the complex transformer and returns a perfectly, fully populated `DashboardData` DTO object.
    *   Test Error Translation Integrity: Configure the underlying API mock to explicitly raise a severe `AuthenticationError`. Mathematically assert that the controller securely catches this and seamlessly returns a safe, generic error message string instead of violently crashing the test runner.
*   **UI Testing Limitations**: We will deliberately not write complex, brittle automated tests for the Streamlit UI logic (`app.py`) itself within the standard Pytest suite due to extreme brittleness. Complete visual correctness is definitively verified via manual UAT.

### Live E2E Testing
*   A comprehensive manual (or script-assisted) E2E run utilizing the `streamlit run app.py` command must be thoroughly performed. This involves a human deliberately entering a highly real, known repository name and visually, mathematically confirming that the entire software pipeline functions correctly from the initial API fetch all the way to the final interactive chart rendering.
