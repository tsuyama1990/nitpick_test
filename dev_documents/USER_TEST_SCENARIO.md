# User Test Scenarios & Master Tutorial Plan

## Tutorial Strategy

The testing and verification of this system are strictly unified under a User Acceptance Testing (UAT) and Tutorial strategy executed via a single interactive Marimo notebook. This approach bridges the gap between automated CI validation and manual developer onboarding.

The core strategy involves designing the notebook to operate in two distinct modes: "Mock Mode" and "Real Mode".

**Mock Mode (CI/No-API-Key Execution):**
When the notebook detects the absence of a `GITHUB_TOKEN` environment variable, it automatically engages Mock Mode. In this state, all network interactions generated by the underlying `GitHubClient` are intercepted using `pytest-httpx` or `unittest.mock`. This allows the notebook to execute synchronously within the automated CI pipeline, asserting that the data transformation pipelines (Polars), local caching mechanisms, and orchestrator logic function perfectly without risking API rate limits or failing due to missing credentials in the sandbox.

**Real Mode (Local Development):**
When a developer clones the repository and configures a valid `.env` file containing a `GITHUB_TOKEN`, the notebook detects the token and engages Real Mode. In this state, mocking is bypassed. The notebook interacts with the live GitHub API, processing real repository data. This serves as a powerful, interactive tutorial, allowing new developers to step through the code, inspect the Polars DataFrames visually, and understand exactly how the system reacts to live network constraints and data structures.

## Tutorial Plan

A **SINGLE** Marimo notebook file must be created to house the entirety of the UAT and tutorial content. Consolidating this into one file drastically reduces complexity and ensures all scenarios are verifiable simultaneously.

**Target File:** `tests/uat/UAT_AND_TUTORIAL.py`

This single file must implement the following sequential scenarios:

1.  **Scenario 1: System Initialization and Dependency Injection (Quick Start)**
    - *Objective:* Demonstrate how the application configuration (`pydantic-settings`), the `GitHubClient`, and the `LocalCache` are instantiated and wired together into the central `GitHubAnalyticsService`.
    - *Verification:* Assert that the `Settings` object correctly identifies if the environment is in Mock or Real mode based on the presence of the `GITHUB_TOKEN`.
2.  **Scenario 2: Data Ingestion and Transformation Pipeline (Advanced)**
    - *Objective:* Trace the lifecycle of a request for a target repository (e.g., `streamlit/streamlit`).
    - *Verification:* Execute the `service.get_dashboard_data()` method. Assert that the resulting dictionary contains valid `RepositoryMetrics` and that the returned Polars DataFrames for `commits_by_date` and `top_committers` possess the strictly defined schemas (correct column names and data types).
3.  **Scenario 3: Local Caching and Rate Limit Protection (Advanced)**
    - *Objective:* Prove that the local Parquet cache successfully intercepts repeated requests to prevent redundant API calls.
    - *Verification:* Execute a second request for the same repository queried in Scenario 2. Use a mock to assert that zero network requests are dispatched during this second call, validating the cache hit mechanism.
4.  **Scenario 4: Graceful Error Handling and Boundary Protection (Advanced)**
    - *Objective:* Demonstrate the system's resilience against invalid inputs.
    - *Verification:* Execute a request for a deliberately malformed or non-existent repository (e.g., `invalid-owner-xyz/non-existent-repo-123`). Assert that the system correctly translates the resulting HTTP 404 error into a specific, application-level `RepositoryNotFoundError` rather than crashing or exposing raw stack traces.

## Tutorial Validation

The Marimo notebook is designed to be self-validating. The cells containing the UAT scenarios must utilize native Python `assert` statements. During CI execution, the notebook will be run programmatically (e.g., via `pytest-marimo` or a direct execution script). If any assertion fails, or if a cell crashes unexpectedly, the validation fails. A successful execution of the notebook from start to finish constitutes proof that the system meets the core requirements defined in the specification and is robust enough for user deployment.
